# Repository Guidelines

This is the Rust rewrite of Sinex. The README describes what works today and
how to run it. The target architecture is
`/realm/project/sinex/analysis/architecture-20261018/sinex-architecture.md`;
planned work is in Beads (`bd` from this checkout). The old Sinex is in Git
history for reference.

## Structure

Read [ARCHITECTURE.md](ARCHITECTURE.md) for how the crates divide the work
and [docs/vocabulary.md](docs/vocabulary.md) for the names of things.

- `crates/sinex-macros`: the `EventPayload` and `DbCheck` derives.
- `crates/sinex-model`: identifiers, the three clocks, record locations,
  equivalence keys, typed payloads (`event_types`), events and batches. No IO.
- `crates/sinex-protocol`: the command table and the producer protocol. No IO.
- `crates/sinex-schema`: the schema declared in Rust and `sinex-schema apply`.
  It has no checked queries, so it builds before any database exists.
- `crates/sinex-store`: admission (the only way events are stored), materials,
  positions, privacy rules, runs, queries. Knows no source by name.
- `crates/sinex-source-core`: the parser trait, drain and shared drivers;
  archive and SQLite drivers are selected by features.
- `crates/sinex-sources`: source families and the live capture loop. Capture
  nodes build without its `full` feature.
- `crates/sinex-sealing`: sealed payloads, keys and encryption.
- `crates/sinex-derivations`: derivations as pure code: fusion rules, metric
  figures and the rest.
- `crates/sinex-analysis`: statistics over derived events as pure code:
  coverage, panels, methods, findings, briefs.
- `crates/sinex-library`: the media library.
- `crates/sinexd`: the daemon: the writer task, source tasks, `backfill`.
- `crates/sinex-session`, `crates/sinex-capture`: the session service and the
  capture-only node, outside producers over the NATS ingress.
- `crates/sinexctl`, `crates/sinex-diagnostics`: the CLI and MCP server, and
  diagnostics that work while the daemon is down.
- `xtask`: developer commands (`check`, `test`, `db`, `boundaries`), built on
  `devkit` from polylogue-sinex-common. Every run is recorded; `xtask status`
  shows what failed last time and `xtask history` reads more.

`xtask boundaries` enforces which crates may depend on which.

`nix/` holds the NixOS module (`nixosModules.default`) and its VM tests
(`nix build .#checks.x86_64-linux.vm-stack`, `vm-topology`, `vm-restore`).
Source and derivation options come from `nix/catalog.json`, generated by
`sinexd admin catalog`; a test fails when it is stale.

The store compiles its SQL against a real schema (SQLx checked queries; no
offline cache). `xtask db ensure` builds the database for the current schema
version and prints its `DATABASE_URL`; xtask commands set it themselves. The
database is named after a hash of the generated DDL and server version, so a
schema change gives a new one and only the query-checking crates recompile.

## Development loop

Optimize for fast integration.

- Every cargo build or test runs as an AgentCTL job (`agentctl project
  operations sinex`). While editing, run selected tests with
  `agentctl job start sinex focused --workspace <worktree> -- -p <package>
  -E 'test(<name>)'`, and selected compilation with `compile -- -p <package>
  [--tests]`, which prepares the schema database when needed and runs `cargo check --locked`
  without adding workspace selection. Package selection limits the build; a
  name filter alone still builds the workspace. `fmt` formats; `check` runs
  fmt, boundaries and clippy against the schema database; `test` runs every
  Rust test under nextest; `package` is the Nix build.
- Start a job, then wait for it in the background with `agentctl job wait
  <id>` and keep working. A failed wait prints the failing tests and the
  `xtask history` pointer.
- Before treating a failure as yours, read the newest `sinex:baseline` job
  (`agentctl job list --project sinex`): the host runs `test` on each new
  master head.
- The pre-push hook (`.githooks/pre-push`) runs `cargo fmt --check` and
  `xtask boundaries` (seconds).
- Land a few large, coherent PRs. Rebase onto `origin/master` before
  pushing; `check` and `test` must pass on the exact head before it merges.
  Master has no branch protection, so merge with `gh pr merge --squash
  --match-head-commit <sha>` once they pass.
- Report what you ran and what you did not. A merge is not evidence of testing.
- Keep the loop fast: compare build, setup and test times separately. When a
  run slows down, inspect its slow tests, resource waits and cleanup before
  increasing timeouts or reducing coverage. Record measurements in Beads.

## Code

- Rust, four-space indent, `rustfmt`.
- A name says what the thing is in ordinary words, local variables included.
  [docs/vocabulary.md](docs/vocabulary.md) lists the concepts and their one
  name each; use those names in code, SQL, wire keys, errors, comments and
  docs, and add a concept there before naming it anywhere else.
- Comments state constraints and reasons, briefly. No status, history, Bead
  IDs, spec or architecture section references in code; Git and Beads hold
  those.
- Tests live in their own files, never inline: a module's unit tests in
  `<module>/tests.rs` declared with `#[cfg(test)] mod tests;`, integration
  tests under the crate's `tests/`. A test that needs PostgreSQL calls `devkit::pg::test_database()`
  for its own copy of the schema template; tests run in parallel under
  `xtask test`. CLI and MCP behavior is tested through the public commands,
  not by widening visibility.
- Register only operations that are implemented. Unsupported requests return a
  typed error, never an empty success. Unknown times stay unknown.
- Do not change stored source material; keep what was captured. Excision,
  which deletes a material holding only the excised records, is the only
  exception.

## Data

The repository is public: fixtures are synthetic, and credentials, real
captures, private reports and real databases stay out of Git. Reading the
operator's real files on this machine for development and measurement is fine.
